## Java 12

JDK 12 was released on March 19, 2019. It was a non-LTS release.

This article covers some of the more notable features:

- [JEP 189: Shenandoah: A Low-Pause-Time Garbage Collector (Experimental)](https://openjdk.org/jeps/189)
- [JEP 325: Switch Expressions (Preview)](https://openjdk.org/jeps/325)
- [JEP 334: JVM Constants API](https://openjdk.org/jeps/334)
- [JEP 344: Abortable Mixed Collections for G1](https://openjdk.org/jeps/344)
- [JEP 346: Promptly Return Unused Committed Memory](https://openjdk.org/jeps/346)

The chart below shows the number of features and release dates for each update from JDK 8 through JDK 25:

![Feature counts and release dates for JDK 8 through JDK 25](https://oss.javaguide.cn/github/javaguide/java/new-features/jdk8~jdk24.png)

### JEP 189: Shenandoah, a Low-Pause-Time Garbage Collector (Experimental)

Shenandoah is a low-pause-time garbage collector led by Red Hat. It aims to keep pauses short and relatively independent of heap size, even with large heaps.

Unlike ZGC, which was open-sourced in Java 11 and required JDK 11, Shenandoah had stable JDK 8u builds. This made it easier to adopt while Java 8 remained widely used.

### JEP 344 and JEP 346: G1 Collector Improvements

Java 12 brought two updates to G1, the default garbage collector:

- **Abortable mixed collections:** JEP 344 split the collection set into mandatory and optional regions to help meet the requested pause-time target. G1 can stop processing the optional regions to stay within that target.
- **Promptly return unused committed memory:** JEP 346 enhanced G1 so it can return Java heap memory to the operating system when the application is idle.

### JEP 334: JVM Constants API

This JEP introduced an API for modeling nominal descriptions of key class-file and runtime artifacts, especially constants loadable from the constant pool.

The API provides interfaces and utility classes for representing and working with constant-pool entries in class files. It includes:

- **Constant descriptor interfaces:** `ConstantDesc` and its subinterfaces for describing different kinds of constants.
- **Constant description types:** `ClassDesc`, `MethodTypeDesc`, `MethodHandleDesc`, `DynamicConstantDesc`, and others.
- **Bootstrap methods:** Support for the `invokedynamic` instruction and dynamic constants.

The API is intended to support use cases such as:

1. **Class-file manipulation:** A standard way to describe and work with class-file constant pools.
2. **Bytecode generation:** Simpler interaction between bytecode-generation frameworks such as ASM and Java code.
3. **Reflection:** More type-safe and expressive reflection operations.
4. **Compiler tools:** Better abstractions for compilers and code-generation tools.

This low-level improvement in Java 12 laid groundwork for later bytecode manipulation and compiler features.

### JEP 325: Switch Expressions (Preview)

Traditional `switch` statements can easily omit a `break`. Repeating `break` also adds noise to the code.

Java 12 enhanced `switch` with an arrow syntax for matching cases, so no `break` is needed.

```java
switch (day) {
    case MONDAY, FRIDAY, SUNDAY -> System.out.println(6);
    case TUESDAY                -> System.out.println(7);
    case THURSDAY, SATURDAY     -> System.out.println(8);
    case WEDNESDAY              -> System.out.println(9);
}
```

## Java 13

JDK 13 was released on September 17, 2019. It was a non-LTS release.

This article covers some of the more notable features:

- [JEP 350: Dynamic CDS Archives](https://openjdk.org/jeps/350)
- [JEP 351: ZGC: Uncommit Unused Memory](https://openjdk.org/jeps/351)
- [JEP 355: Text Blocks (Preview)](https://openjdk.org/jeps/355)
- [JEP 354: Switch Expressions (Second Preview)](https://openjdk.org/jeps/354)

The chart below shows the number of features and release dates for each update from JDK 8 through JDK 24:

![](https://oss.javaguide.cn/github/javaguide/java/new-features/jdk8~jdk24.png)

### JEP 351: ZGC Uncommit Unused Memory

In practice, the experimental ZGC introduced in Java 11 did not proactively return unused memory to the operating system.

The ZGC heap consists of regions called ZPages. When a GC cycle empties a ZPage, it is released to the **ZPageCache**. The cache organizes ZPages by size and least-recently-used (LRU) order.

In Java 13, ZGC began returning pages identified as unused for a long time to the operating system, where other processes could use them.

### JEP 350: Dynamic CDS Archives

Java 13 further simplified, improved, and extended Application Class-Data Sharing (AppCDS), introduced in Java 10. It **allows classes to be archived dynamically when a Java application exits**. The archive can include loaded application and library classes that are not part of the default base CDS archive.

This makes [AppCDS](https://openjdk.java.net/jeps/310) easier to use: users no longer need to run an application in advance to create a class list for each application.

```bash
java -XX:ArchiveClassesAtExit=my_app_cds.jsa -cp my_app.jar
java -XX:SharedArchiveFile=my_app_cds.jsa -cp my_app.jar
```

### JEP 355: Text Blocks (Preview)

Text blocks address the awkward ways of writing multiline strings in Java, such as escaping line breaks or concatenating strings. They use **three double quotes** to delimit multiline text.

In Java 13, everything between a pair of `"""` delimiters is treated as part of the string, including line breaks.

Before text blocks, HTML could be written as:

```java
String json ="{\n" +
              "   \"name\":\"mkyong\",\n" +
              "   \"age\":38\n" +
              "}\n";
```

With text blocks:

```java
 String json = """
                {
                    "name":"mkyong",
                    "age":38
                }
                """;
```

Before text blocks, SQL could be written as:

```sql
String query = "SELECT `EMP_ID`, `LAST_NAME` FROM `EMPLOYEE_TB`\n" +
               "WHERE `CITY` = 'INDIANAPOLIS'\n" +
               "ORDER BY `EMP_ID`, `LAST_NAME`;\n";
```

With text blocks:

```sql
String query = """
               SELECT `EMP_ID`, `LAST_NAME` FROM `EMPLOYEE_TB`
               WHERE `CITY` = 'INDIANAPOLIS'
               ORDER BY `EMP_ID`, `LAST_NAME`;
               """;
```

For methods related to text blocks (`formatted()`, `stripIndent()`, and `translateEscapes()`), see [String Enhancements for Text Blocks](#string-enhancements-for-text-blocks) below.

### JEP 354: Switch Expressions (Second Preview)

The second preview of `switch` expressions added the `yield` keyword, which exits a `switch` branch and produces a value.

`return` exits the current method and returns a result. `yield` exits the current `switch` branch and provides the value of the `switch` expression. A `switch` expression must cover every possible input, but it does not need a `default` branch if all possible values are already covered.

```java
 private static String descLanguage(String name) {
        return switch (name) {
            case "Java": yield "object-oriented, platform independent and secured";
            case "Ruby": yield "a programmer's best friend";
            default: yield name +" is a good language";
        };
 }
```

## API Enhancements

Not every API change is delivered through a JEP (Java Enhancement Proposal).

In JDK development, **JEPs** are generally used for major changes, such as new language features (`switch` expressions), JVM mechanisms (ZGC), or large library refactors. Adding a few methods to an existing class, such as `String.indent()`, is usually routine library maintenance. JDK developers submit and review these changes through **JBS (JDK Bug System)** tickets, and they ship with a release.

### String Enhancements

Java 12 added two String methods.

#### `indent()`

The `indent()` method adds or removes indentation from a string.

```java
String text = "Java";
// Indent by four spaces.
text = text.indent(4);
System.out.println(text);
text = text.indent(-10);
System.out.println(text);
```

Output:

```plain
     Java
Java
```

#### `transform()`

The `transform()` method applies a function to a string and returns the result.

```java
String result = "foo".transform(input -> input + " bar");
System.out.println(result); // foo bar
```

### Files Enhancements

Java 12 added `mismatch()` to compare two files:

```java
public static long mismatch(Path path, Path path2) throws IOException
```

`mismatch()` compares two files and returns the position of the first mismatching byte, or `-1L` if the files are identical.

Example: the files have identical contents.

```java
Path filePath1 = Files.createTempFile("file1", ".txt");
Path filePath2 = Files.createTempFile("file2", ".txt");
Files.writeString(filePath1, "Java 12 Article");
Files.writeString(filePath2, "Java 12 Article");

long mismatch = Files.mismatch(filePath1, filePath2);
assertEquals(-1, mismatch);
```

Example: the files have different contents.

```java
Path filePath3 = Files.createTempFile("file3", ".txt");
Path filePath4 = Files.createTempFile("file4", ".txt");
Files.writeString(filePath3, "Java 12 Article");
Files.writeString(filePath4, "Java 12 Tutorial");

long mismatch = Files.mismatch(filePath3, filePath4);
assertEquals(8, mismatch);
```

### NumberFormat Enhancements

Java 12 added support for compact number formatting to `NumberFormat`:

```java
NumberFormat fmt = NumberFormat.getCompactNumberInstance(Locale.US, NumberFormat.Style.SHORT);
String result = fmt.format(1000);
System.out.println(result);
```

Output:

```plain
1K
```

### Socket API Enhancements

Java 13 rewrote the Socket API internals. `NioSocketImpl` directly replaces `PlainSocketImpl` and uses locks from `java.util.concurrent` instead of synchronized methods. To use the old implementation, set `-Djdk.net.usePlainSocketImpl=true`.

Java 13 uses the new Socket implementation by default.

```java
public final class NioSocketImpl extends SocketImpl implements PlatformSocketImpl {
}
```

### FileSystems Enhancements

Java 13 added these methods to `FileSystems`, making it easier to use file-system providers that treat a file's contents as a file system:

- `newFileSystem(Path)`
- `newFileSystem(Path, Map<String, ?>)`
- `newFileSystem(Path, Map<String, ?>, ClassLoader)`

### String Enhancements for Text Blocks

Java 13 introduced text blocks as a preview feature and added three `String` methods for working with them:

- `formatted(Object... args)`: Similar to `String.format()`, this method formats text blocks.
- `stripIndent()`: Removes incidental leading whitespace from each line of a text block.
- `translateEscapes()`: Converts escape sequences such as _"\\\t"_ to _"\t"_.

Because text blocks were still a preview feature and could change or be removed in a future release, these methods were marked for removal.

```java
@Deprecated(forRemoval=true, since="13")
public String stripIndent() {
}
@Deprecated(forRemoval=true, since="13")
public String formatted(Object... args) {

}
@Deprecated(forRemoval=true, since="13")
public String translateEscapes() {
}
```

For more about text blocks, see [JEP 355: Text Blocks (Preview)](#jep-355-text-blocks-preview).

## Additional Notes

### Preview Features

Oracle describes a preview feature as follows: `This is a preview feature, which is a feature whose design, specification, and implementation are complete, but is not permanent, which means that the feature may exist in a different form or not at all in future JDK releases. To compile and run code that contains preview features, you must specify additional command-line options.`

In other words, a preview feature has a complete design, specification, and implementation, but is not permanent. It may change or disappear in a later JDK release. Compiling and running code that uses preview features requires additional command-line options.

For example, `switch` expressions were previewed in Java 12, refined in Java 13, and became a standard language feature in Java 14. Once standardized, their syntax and semantics became part of the Java SE specification, and preview options were no longer required.

This process reflects the care taken when adding features to the JDK as a standard platform. Preview features should be used with caution because their practical value still needs to be validated through use.

### JVM Improvements

Each Java release brings JVM improvements, such as updates to existing garbage collectors, new collectors, and the removal of outdated collectors.

The overall goal is **efficient, low-latency garbage collection**.

Application developers may focus on new language features, but organizations deciding whether to upgrade Java may care more about **improvements to the JVM runtime**.
