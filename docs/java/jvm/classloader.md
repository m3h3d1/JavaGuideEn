## A Quick Review of Class Loading

Before looking at class loaders and the parent delegation model, let's briefly review the class loading process.

- Class loading consists of **loading -> linking -> initialization**.
- Linking has three steps: **verification -> preparation -> resolution**.

![Class loading process](https://oss.javaguide.cn/github/javaguide/java/jvm/class-loading-procedure.png)

Loading is the first step of class loading. It mainly does the following:

1. Obtain the binary byte stream that defines the class by its fully qualified name.
2. Convert the static structure represented by the byte stream into runtime structures in the method area.
3. Create a `Class` object in memory to provide access to the class data in the method area.

## Class Loaders

### Introduction

Class loaders have existed since JDK 1.0. They were first introduced to support Java Applets, which are now obsolete. Over time, they became an important part of Java, allowing classes to be loaded into the JVM and executed at runtime.

The official API documentation explains:

> A class loader is an object that is responsible for loading classes. The class ClassLoader is an abstract class. Given the binary name of a class, a class loader should attempt to locate or generate data that constitutes a definition for the class. A typical strategy is to transform the name into a file name and then read a "class file" of that name from a file system.
>
> Every Class object contains a reference to the ClassLoader that defined it.
>
> Class objects for array classes are not created by class loaders, but are created automatically as required by the Java runtime. The class loader for an array class, as returned by Class.getClassLoader() is the same as the class loader for its element type; if the element type is a primitive type, then the array class has no class loader.

In other words:

> A class loader is an object responsible for loading classes. `ClassLoader` is an abstract class. Given a class's binary name, a class loader attempts to locate or generate the data that defines it. A common strategy is to convert the name to a file name and read the corresponding class file from the file system.
>
> Every non-array class or interface has a reference to the `ClassLoader` that defined it. Array classes are created automatically by the JVM as needed. An array of reference types uses the class loader of its component type; an array of primitive types has no class loader, so `getClassLoader()` returns `null`.

This means:

- A class loader loads classes and performs the loading step of the class loading process.
- Every non-array class or interface records the `ClassLoader` that defined it.
- Array classes have no corresponding binary byte stream, so the JVM creates them directly. An array of reference types uses the defining loader of its component type; an array of primitive types has no class loader.

```java
class Class<T> {
  ...
  private final ClassLoader classLoader;
  @CallerSensitive
  public ClassLoader getClassLoader() {
     //...
  }
  ...
}
```

In short, **a class loader dynamically loads Java bytecode (`.class` files) into the JVM and creates a `Class` object for each class in memory.** The bytecode may come from Java source (`.java`) compiled by `javac`, be generated by a tool, or be downloaded over a network.

Class loaders can also load resources used by Java applications, such as text, images, configuration files, and videos. This article focuses on their main function: loading classes.

### Class Loading Rules

The JVM does not load every class at startup. It loads classes on demand, which helps reduce memory use.

When loading a class, `ClassLoader#loadClass` first checks `findLoadedClass` to see whether the JVM has recorded this loader as an initiating loader for the binary name. If so, it returns the class; otherwise, it continues delegating or searching. A class loader cannot define the same binary name more than once.

```java
// These fields and methods are from the JDK 8 ClassLoader implementation and illustrate how that version tracks loaded classes.
public abstract class ClassLoader {
  ...
  private final ClassLoader parent;
  // Classes loaded by this class loader.
  private final Vector<Class<?>> classes = new Vector<>();
  // Called by the VM to record each class loaded by this class loader.
  void addClass(Class<?> c) {
        classes.addElement(c);
   }
  ...
}
```

### Summary of Class Loaders

The three commonly discussed class loaders in JDK 8 are:

1. **`BootstrapClassLoader`**: The top-level built-in JVM loader. It is usually represented as `null` in the Java API and has no parent. In JDK 8 HotSpot, it primarily loads core runtime libraries such as `rt.jar`, along with classes from paths specified by `-Xbootclasspath`.
2. **`ExtensionClassLoader`**: Primarily loads JARs and classes from `%JRE_HOME%/lib/ext` and paths specified by the `java.ext.dirs` system property.
3. **`AppClassLoader`**: The application class loader. It loads JARs and classes from the current application's classpath.

> 🌈 A little more context:
>
> - **`rt.jar`**: `rt` stands for "runtime." In JDK 8, `rt.jar` contains the core Java class libraries, including commonly used packages such as `java.util.*`, `java.io.*`, `java.nio.*`, `java.lang.*`, `java.sql.*`, and `java.math.*`.
> - Java 9 introduced the module system and removed `rt.jar` and the extension directory mechanism. The platform class loader replaced the extension class loader. The bootstrap, platform, and application class loaders define different runtime modules; it is inaccurate to say that the platform class loader loads every module except `java.base`.

Users can also add custom class loaders for specific needs. For example, a custom class loader can decrypt Java bytecode (`.class` files) as it loads them.

![Class loader hierarchy](https://oss.javaguide.cn/github/javaguide/java/jvm/class-loader-parents-delegation-model.png)

The bootstrap class loader is built into the VM and is usually represented as `null` in the Java API. The platform, application, and most custom class loaders are instances of `ClassLoader`. Applications can define custom class loaders to control how classes are found.

Each `ClassLoader` can use `getParent()` to retrieve its parent. If this returns `null`, the parent is the `BootstrapClassLoader`.

```java
public abstract class ClassLoader {
  ...
  // Parent class loader.
  private final ClassLoader parent;
  @CallerSensitive
  public final ClassLoader getParent() {
     //...
  }
  ...
}
```

**Why does `getClassLoader()` return `null` for a class defined by the bootstrap class loader?** The bootstrap class loader is built into the JVM, and the Java API conventionally represents it as `null`. Its implementation language is not specified by Java.

Here's a small example that prints a class loader and its parents:

```java
public class PrintClassLoaderTree {

    public static void main(String[] args) {

        ClassLoader classLoader = PrintClassLoaderTree.class.getClassLoader();

        StringBuilder split = new StringBuilder("|--");
        boolean needContinue = true;
        while (needContinue){
            System.out.println(split.toString() + classLoader);
            if(classLoader == null){
                needContinue = false;
            }else{
                classLoader = classLoader.getParent();
                split.insert(0, "\t");
            }
        }
    }

}
```

Output (JDK 8):

```plain
|--sun.misc.Launcher$AppClassLoader@18b4aac2
    |--sun.misc.Launcher$ExtClassLoader@53bd815b
        |--null
```

The output shows that:

- The `ClassLoader` for our `PrintClassLoaderTree` class is `AppClassLoader`.
- The parent of `AppClassLoader` is `ExtClassLoader`.
- The parent of `ExtClassLoader` is the bootstrap class loader, which is why the output is `null`.

### Custom Class Loaders

As mentioned above, all class loaders other than `BootstrapClassLoader` are implemented in Java and extend `java.lang.ClassLoader`. To create a custom class loader, extend the `ClassLoader` abstract class.

The `ClassLoader` class has two key methods:

- `protected Class loadClass(String name, boolean resolve)`: Loads a class with the specified binary name and implements parent delegation. `name` is the class's binary name. If `resolve` is true, the method calls `resolveClass(Class<?> c)` to link the class.
- `protected Class findClass(String name)`: Finds a class by its binary name. The default implementation throws `ClassNotFoundException`.

The official API documentation states:

> Subclasses of `ClassLoader` are encouraged to override `findClass(String name)`, rather than this method.
>
> Subclasses of `ClassLoader` are encouraged to override `findClass(String name)` rather than `loadClass(String name, boolean resolve)`.

To preserve parent delegation, override `findClass()`. Classes that cannot be loaded by a parent will eventually be handled by this method. To change the delegation behavior, override `loadClass()`.

## The Parent Delegation Model

### Introduction

Java has several kinds of class loaders. Which one loads a class? The parent delegation model helps answer that question.

The official documentation explains:

> The ClassLoader class uses a delegation model to search for classes and resources. Each instance of ClassLoader has an associated parent class loader. When requested to find a class or resource, a ClassLoader instance will delegate the search for the class or resource to its parent class loader before attempting to find the class or resource itself. The virtual machine's built-in class loader, called the "bootstrap class loader", does not itself have a parent but may serve as the parent of a ClassLoader instance.

In other words:

> The `ClassLoader` class uses a delegation model to search for classes and resources. Each `ClassLoader` instance has an associated parent. When asked to find a class or resource, it delegates the search to its parent before trying to find it itself.
> The built-in class loader called the "bootstrap class loader" has no parent, but it can be the parent of another `ClassLoader` instance.

This means:

- `ClassLoader` uses delegation to search for classes and resources.
- Under the parent delegation model, every loader except the top-level bootstrap class loader has a parent.
- A `ClassLoader` delegates searches to its parent before trying to find a class or resource itself.

The hierarchy between class loaders shown below is known as the **parent delegation model**.

![Class loader hierarchy](https://oss.javaguide.cn/github/javaguide/java/jvm/class-loader-parents-delegation-model.png)

⚠️ Note: Parent delegation is not mandatory; it is the approach recommended by the JDK. It can be changed to meet specific requirements, as described later.

The term "parent" in this model can be confusing. It does not mean that each loader has two parents, such as a `MotherClassLoader` and a `FatherClassLoader`. The model describes a parent-child hierarchy. The established term is "parent delegation," so it is fine to use it as long as the hierarchy is clear.

The parent-child relationship between class loaders is generally implemented through composition, not inheritance. This lets a loader reuse its parent's behavior.

```java
public abstract class ClassLoader {
  ...
  // Composition.
  private final ClassLoader parent;
  protected ClassLoader(ClassLoader parent) {
       this(checkCreateClassLoader(), parent);
  }
  ...
}
```

Object-oriented design has a well-known principle: **favor composition over inheritance.**

### How Parent Delegation Works

The main logic of parent delegation is in `java.lang.ClassLoader.loadClass()`. The following excerpt is from JDK 8:

```java
protected Class<?> loadClass(String name, boolean resolve)
    throws ClassNotFoundException
{
    synchronized (getClassLoadingLock(name)) {
        // First, check whether the class has already been loaded.
        Class c = findLoadedClass(name);
        if (c == null) {
            // If c is null, the class has not been loaded.
            long t0 = System.nanoTime();
            try {
                if (parent != null) {
                    // If there is a parent loader, ask it to load the class.
                    c = parent.loadClass(name, false);
                } else {
                    // If there is no parent loader, ask the bootstrap loader to load the class.
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // The non-null parent loader could not find the class.
            }

            if (c == null) {
                // If the parent could not load the class, call findClass().
                // Custom class loaders can override this method.
                long t1 = System.nanoTime();
                c = findClass(name);

                // Record class loader statistics.
                sun.misc.PerfCounter.getParentDelegationTime().addTime(t1 - t0);
                sun.misc.PerfCounter.getFindClassTime().addElapsedTimeFrom(t1);
                sun.misc.PerfCounter.getFindClasses().increment();
            }
        }
        if (resolve) {
            // Link the class.
            resolveClass(c);
        }
        return c;
    }
}
```

When a class loader receives a request, it first delegates the request to its parent. It tries to load the class itself only if the parent cannot find it.

The code above can be summarized as follows:

- The system first checks whether the class has already been loaded by the current loader. If so, it returns the class; otherwise, it continues. Each parent loader performs the same check.
- A loader first delegates the request to its parent by calling the parent's `loadClass()`. Requests eventually reach the top-level bootstrap class loader.
- If a parent cannot find the class, the child loader tries to load it by calling its own `findClass()` method.
- If the child loader cannot find the class either, it throws `ClassNotFoundException`.

🌈 A little more context:

**How the JVM determines whether two Java classes are the same:** It considers both the class's binary name and the class loader that defined it. The classes are the same only if both match. Even if two classes come from the same `Class` file and are loaded by the same JVM, different defining class loaders make them distinct types.

### Benefits of Parent Delegation

Parent delegation is an important part of Java's class loading mechanism. Delegating to parents first helps classes in the same delegation chain reuse types already defined by a parent and reduces the risk of application code impersonating platform APIs. It does not prevent independent class loaders from defining classes with the same name.

The JVM distinguishes runtime types by their binary names and defining class loaders. Parent delegation gives platform classes priority to be defined by the corresponding built-in loader. However, not every core or platform API is loaded by the bootstrap loader: since JDK 9, the platform class loader defines platform classes as well.

For example, the JVM delegates requests for core classes such as `java.lang.Object` to `BootstrapClassLoader` first. In addition, `ClassLoader#preDefineClass` validates class names during definition and rejects names that start with `java.`, so a custom loader cannot define a fake core class.

You might ask, "Couldn't I just bypass parent delegation?"

Even if an attacker bypasses parent delegation, Java has lower-level protections for core libraries. Before defining a class, `ClassLoader.preDefineClass` validates its name. A name starting with `java.` triggers `SecurityException`, preventing malicious code from defining a fake core class.

Here is the JDK 8 implementation of `ClassLoader#preDefineClass`:

```java
private ProtectionDomain preDefineClass(String name,
                                            ProtectionDomain pd)
    {
        // Check that the class name is valid.
        if (!checkName(name)) {
            throw new NoClassDefFoundError("IllegalName: " + name);
        }

        // Prevent classes from being defined in the "java.*" package.
        // This check helps prevent malicious code from replacing core Java classes.
        // JDK 9 strengthened preDefineClass with the platform class loader.
        if ((name != null) && name.startsWith("java.")) {
            throw new SecurityException
                ("Prohibited package name: " +
                 name.substring(0, name.lastIndexOf('.')));
        }

         // Use the default domain if no ProtectionDomain was specified.
        if (pd == null) {
            pd = defaultDomain;
        }

        if (name != null) {
            checkCerts(name, pd.getCodeSource());
        }

        return pd;
    }
```

JDK 9 introduced the platform class loader, which can be obtained with `ClassLoader.getPlatformClassLoader()`. The restriction on defining classes in `java.*` still applies, though the implementation differs from JDK 8.

### Breaking Parent Delegation

~~To avoid parent delegation, we can define a custom class loader and override `loadClass()`.~~

**🐛 Correction (see [issue 871](https://github.com/Snailclimb/JavaGuide/issues/871))**: A custom loader should extend `ClassLoader`. To preserve parent delegation, override `findClass()`. Classes that cannot be loaded by a parent will eventually be handled by this method. To break parent delegation, override `loadClass()`.

Why does overriding `loadClass()` break parent delegation? The delegation flow described above explains why:

> When loading a class, a class loader first delegates the request to its parent by calling the parent's `loadClass()` method.

Overriding `loadClass()` lets us change this flow. For example, a child loader can try to load the class before delegating to its parent, or search another location after the parent returns. The custom loader defines the behavior to meet the application's needs.

Tomcat uses a custom `WebAppClassLoader` to load classes from a web application's directories before searching other locations. This changes parent delegation and helps isolate classes between web applications.

Tomcat's class loader hierarchy is shown below:

![Tomcat class loader hierarchy](https://oss.javaguide.cn/github/javaguide/java/jvm/tomcat-class-loader-parents-delegation-model.png)

Modern Tomcat uses the `Bootstrap -> System -> Common -> WebappX` hierarchy by default. The loaders search these locations:

- `Common` searches locations configured by `common.loader` in `$CATALINA_BASE/conf/catalina.properties`. By default, these mainly include `$CATALINA_BASE/lib` and `$CATALINA_HOME/lib`.
- Each `WebappX` loader handles `/WEB-INF/classes` and `/WEB-INF/lib/*.jar` for its web application.
- `Server` and `Shared` loaders are not defined by default. They appear in more complex hierarchies only when `server.loader` or `shared.loader` is configured.

The delegation relationships in the diagram show that:

- Classes visible to `Common` can be shared by Tomcat's internal components and all web applications.
- If explicitly configured, `Server` is visible only to Tomcat, while `Shared` is visible to all web applications. These loaders are absent by default, so each web application's loader uses `Common` as its parent.
- Each web application gets its own `WebAppClassLoader`. The thread that starts the application uses that loader as its context class loader. The `WebAppClassLoader` instances are isolated from one another, which isolates classes between web applications.

Custom class loaders alone do not meet every need. In some cases, a higher-level loader needs to load a class that only a lower-level loader can find.

For example, an SPI interface such as `java.sql.Driver` is provided by the Java libraries, while its implementation, such as `com.mysql.cj.jdbc.Driver`, comes from a third-party provider and is loaded by an application or custom class loader. By default, the loader that loads a class also loads its dependencies. If the loader for the SPI interface (`BootstrapClassLoader`) also had to load the implementation, it would fail: under parent delegation, it cannot delegate the search to a child loader.

Note that JDK 9 introduced modules and placed the JDBC API in the `java.sql` module. It is no longer loaded directly by `BootstrapClassLoader`; the platform class loader defines it.

```java
public class ClassLoaderTest {
    public static void main(String[] args) throws ClassNotFoundException {
        Class<?> clazz = Class.forName("java.sql.Driver");
        ClassLoader loader = clazz.getClassLoader();
        System.out.println("Loader for java.sql.Driver: " + loader);

        // With .jdks/corretto-1.8.0_442/bin/java: Loader for java.sql.Driver: null

        // With .jdks/jbr-17.0.12/bin/java: Loader for java.sql.Driver: jdk.internal.loader.ClassLoaders$PlatformClassLoader@30f39991
    }
}
```

Another example: suppose a project uses Spring JARs shared between web applications, so Tomcat loads them with `SharedClassLoader`. The project also has business classes that implement Spring interfaces or use Spring annotations. The loader that loaded Spring (`SharedClassLoader`) may also be asked to load these business classes. But they are in the web application's directories, outside `SharedClassLoader`'s search path, so it cannot find them.

The **thread context class loader (`ThreadContextClassLoader`)** can solve this problem.

In the Spring example, Spring uses the current thread's context class loader when it needs to load a business class. As mentioned above, each web application has its own `WebAppClassLoader`, which is set as the context class loader on the thread that starts the application. This lets the higher-level `SharedClassLoader` use the child `WebAppClassLoader` to load business classes, allowing a higher-level component to access classes through a lower-level loader.

The thread context class loader is stored in thread-local state and retrieved when needed. It is usually set by the application or a container such as Tomcat.

In `java.lang.Thread`, `getContextClassLoader()` and `setContextClassLoader(ClassLoader cl)` retrieve and set the thread's context class loader. If it is not set explicitly, a thread inherits the context class loader of its parent thread.

Spring can retrieve the thread context class loader as follows:

```java
cl = Thread.currentThread().getContextClassLoader();
```
