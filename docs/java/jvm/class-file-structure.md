## A quick review of bytecode

In Java, code understood by the JVM is called `bytecode` and is stored in files with the `.class` extension. Bytecode targets the virtual machine rather than any specific processor. This lets Java improve on the runtime efficiency of traditional interpreted languages while retaining portability. Because bytecode is not tied to a specific machine, a Java program can run on computers with different operating systems without recompilation.

Languages such as Clojure (a Lisp dialect), Groovy, Scala, JRuby, and Kotlin also run on the JVM. The diagram below shows how different compilers generate `.class` files that run on the JVM. You can inspect the binary format of a `.class` file with a tool such as [WinHex](https://www.x-ways.net/winhex/).

![Programming languages that run on the Java Virtual Machine](https://oss.javaguide.cn/github/javaguide/java/basis/java-virtual-machine-program-language-os.png)

The `.class` file is an important bridge that lets different languages run on the JVM, and it is also a key reason Java is cross-platform.

## Class file structure

The Java Virtual Machine Specification defines a class file using the `ClassFile` structure, which is somewhat like a C struct.

The `ClassFile` structure is as follows:

```java
ClassFile {
    u4             magic; // Class file identifier
    u2             minor_version; // Minor class file version
    u2             major_version; // Major class file version
    u2             constant_pool_count; // Number of constant pool entries
    cp_info        constant_pool[constant_pool_count-1]; // Constant pool
    u2             access_flags; // Class access flags
    u2             this_class; // Current class
    u2             super_class; // Superclass
    u2             interfaces_count; // Number of interfaces
    u2             interfaces[interfaces_count]; // Interfaces implemented by the class
    u2             fields_count; // Number of fields
    field_info     fields[fields_count]; // Fields declared by the class
    u2             methods_count; // Number of methods
    method_info    methods[methods_count]; // Methods declared by the class
    u2             attributes_count; // Number of attributes in this class's attribute table
    attribute_info attributes[attributes_count]; // Attribute table
}
```

The `ClassFile` structure shows how a class file is organized.

![Analysis of ClassFile contents](https://oss.javaguide.cn/java-guide-blog/16d5ec47609818fc.jpeg)

The following image shows a class file viewed with the IntelliJ IDEA plugin `jclasslib`, which provides a more visual representation of its structure.

With `jclasslib`, you can inspect a class's bytecode file as well as its basic information, constant pool, interfaces, attributes, and methods.

The following sections describe some of the components of a class file.

### Magic number

```java
    u4             magic; // Class file identifier
```

The first four bytes of every class file are its magic number. Its only purpose is to **identify whether the file is a class file that the virtual machine can accept**. The Java specification defines the fixed value `0xCAFEBABE`. If a file does not begin with this value, the JVM rejects it.

### Class file version (minor and major versions)

```java
    u2             minor_version; // Minor class file version
    u2             major_version; // Major class file version
```

The four bytes immediately after the magic number store the class file version: bytes 5 and 6 are the **minor version**, and bytes 7 and 8 are the **major version**.

The major version increases with each Java release (for example, Java 8 and Java 9). Use `javap -v` to quickly check a class file's version.

A newer JVM can run class files generated by an older compiler, but an older JVM cannot run class files generated by a newer compiler. In practice, make sure the JDK version used for development is compatible with the production environment.

### Constant pool

```java
    u2             constant_pool_count; // Number of constant pool entries
    cp_info        constant_pool[constant_pool_count-1]; // Constant pool
```

The constant pool follows the minor and major version numbers. Its entry count is `constant_pool_count - 1` (**the constant pool counter starts at 1, leaving entry 0 unused; index 0 means “no constant pool entry is referenced”**).

The constant pool stores two kinds of values: literals and symbolic references. Literals are similar to constants in Java source code, such as text strings and `final` values. Symbolic references are a compiler concept and include:

- Fully qualified names of classes and interfaces
- Field names and descriptors
- Method names and descriptors

Each constant pool entry is a table. The current Java Virtual Machine Specification defines 17 kinds of constant pool entries. They share one feature: **each begins with a `u1` `tag` that identifies the entry type.**

| Type                               | Tag | Description                           |
| ---------------------------------- | --- | ------------------------------------- |
| `CONSTANT_Utf8_info`               | 1   | UTF-8 encoded string                  |
| `CONSTANT_Integer_info`            | 3   | Integer literal                       |
| `CONSTANT_Float_info`              | 4   | Floating-point literal                |
| `CONSTANT_Long_info`               | 5   | Long integer literal                  |
| `CONSTANT_Double_info`             | 6   | Double-precision literal              |
| `CONSTANT_Class_info`              | 7   | Class or interface symbolic reference |
| `CONSTANT_String_info`             | 8   | String literal                        |
| `CONSTANT_FieldRef_info`           | 9   | Field symbolic reference              |
| `CONSTANT_MethodRef_info`          | 10  | Class method symbolic reference       |
| `CONSTANT_InterfaceMethodRef_info` | 11  | Interface method symbolic reference   |
| `CONSTANT_NameAndType_info`        | 12  | Field or method name and descriptor   |
| `CONSTANT_MethodType_info`         | 16  | Method type                           |
| `CONSTANT_MethodHandle_info`       | 15  | Method handle                         |
| `CONSTANT_Dynamic_info`            | 17  | Dynamically computed constant         |
| `CONSTANT_InvokeDynamic_info`      | 18  | Dynamic call site                     |
| `CONSTANT_Module_info`             | 19  | Module                                |
| `CONSTANT_Package_info`            | 20  | Package in a module                   |

Use `javap -v ClassName` to inspect a `.class` file's constant pool. To write the output to a file, use `javap -v ClassName > temp.txt`.

### Access flags

```java
    u2             access_flags; // Class access flags
```

The two bytes after the constant pool contain the access flags. They identify class- or interface-level properties, such as whether this is a class or interface, whether it is `public` or `abstract`, and, for a class, whether it is `final`.

### Indexes for this class, its superclass, and its interfaces

```java
    u2             this_class; // Current class
    u2             super_class; // Superclass
    u2             interfaces_count; // Number of interfaces
    u2             interfaces[interfaces_count]; // Interfaces implemented by the class
```

The class index, superclass index, and interface index table define a Java class's inheritance relationships. They appear in that order after the access flags.

The class index identifies the class's fully qualified name, and the superclass index identifies its superclass. Java supports single inheritance, so there is only one superclass index. Every Java class except `java.lang.Object` has a superclass, so its superclass index is nonzero.

The interface index table lists the interfaces implemented by the class, in the same left-to-right order as they appear after `implements` (or after `extends` if the class file represents an interface).

### Field table

```java
    u2             fields_count; // Number of fields
    field_info     fields[fields_count]; // Fields declared by the class
```

The field table (`field_info`) describes variables declared in a class or interface. It includes class variables and instance variables, but not local variables declared inside methods.

**Structure of `field_info`:**

![Structure of the field table](https://oss.javaguide.cn/github/javaguide/java/%E5%AD%97%E6%AE%B5%E8%A1%A8%E7%9A%84%E7%BB%93%E6%9E%84.png)

- **access_flags:** The field's scope (`public`, `private`, or `protected`), whether it is an instance or class variable (`static`), whether it is excluded from serialization (`transient`), whether it is immutable (`final`), and whether reads and writes must use main memory (`volatile`).
- **name_index:** A constant pool reference to the field name.
- **descriptor_index:** A constant pool reference to the field or method descriptor.
- **attributes_count:** The number of additional attributes for the field.
- **attributes[attributes_count]:** The field's attribute data.

Each modifier above is a boolean value, so it can be represented by a flag. A field's name and data type can vary, so the class file refers to entries in the constant pool to describe them.

**Possible field access flag values:**

![Possible field access flag values](https://oss.javaguide.cn/github/javaguide/java/jvm/class-file-fields-access_flag.png)

### Method table

```java
    u2             methods_count; // Number of methods
    method_info    methods[methods_count]; // Methods declared by the class
```

`methods_count` is the number of methods, and each `method_info` entry describes one method.

The class file describes methods in almost the same way as fields. Like the field table, the method table contains access flags, a name index, a descriptor index, and an attribute table.

**Structure of `method_info`:**

![Structure of the method table](https://oss.javaguide.cn/github/javaguide/java/%E6%96%B9%E6%B3%95%E8%A1%A8%E7%9A%84%E7%BB%93%E6%9E%84.png)

**Possible method access flag values:**

![Possible method access flag values](https://oss.javaguide.cn/github/javaguide/java/jvm/class-file-methods-access_flag.png)

The `volatile` and `transient` modifiers cannot be applied to methods, so the method access flags do not include them. Methods can use modifiers such as `synchronized`, `native`, and `abstract`, so the table includes corresponding flags.

### Attribute table

```java
   u2             attributes_count; // Number of attributes in this class's attribute table
   attribute_info attributes[attributes_count]; // Attribute table
```

The class file, field table, and method table can each have an attribute table containing information for specific use cases. Unlike other class file structures, attributes do not need to appear in a strict order. A compiler can add custom attributes as long as their names do not duplicate existing ones; the JVM ignores attributes it does not recognize.
