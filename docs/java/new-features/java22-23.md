## JDK 23

### JEP 455: Primitive Types in Patterns, `instanceof`, and `switch` (Preview)

Before JEP 455, `instanceof` supported only reference types, and `case` labels in `switch` expressions and statements could use only integer literals, enum constants, and string literals.

The JEP 455 preview extended `instanceof` and `switch` to all primitive types: `byte`, `short`, `char`, `int`, `long`, `float`, `double`, and `boolean`.

```java
// Traditional form
if (i >= -128 && i <= 127) {
    byte b = (byte)i;
    ... b ...
}

// With instanceof pattern matching
if (i instanceof byte b) {
    ... b ...
}

long v = ...;
// Traditional form
if (v == 1L) {
    // ...
} else if (v == 2L) {
    // ...
} else if (v == 10_000_000_000L) {
    // ...
}

// Use long case labels
switch (v) {
    case 1L:
        // ...
        break;
    case 2L:
        // ...
        break;
    case 10_000_000_000L:
        // ...
        break;
    default:
        // ...
}
```

### JEP 466: Class-File API (Second Preview)

The Class-File API was previewed for the first time in JDK 22 through [JEP 457](https://openjdk.org/jeps/457).

The API provides a standard way to parse, generate, and transform Java class files, reducing the need for third-party libraries such as ASM.

```java
// Create a ClassFile object, the entry point for working with class files.
ClassFile cf = ClassFile.of();
// Parse the byte array into a ClassModel.
ClassModel classModel = cf.parse(bytes);

// Build a new class file, removing all methods whose names start with "debug".
byte[] newBytes = cf.build(classModel.thisClass().asSymbol(),
        classBuilder -> {
            // Iterate over all class elements.
            for (ClassElement ce : classModel) {
                // Check whether this is a method whose name starts with "debug".
                if (!(ce instanceof MethodModel mm
                        && mm.methodName().stringValue().startsWith("debug"))) {
                    // Add it to the new class file.
                    classBuilder.with(ce);
                }
            }
        });
```

### JEP 467: Markdown Documentation Comments

Javadoc comments can use Markdown syntax instead of relying only on HTML and Javadoc tags.

Markdown is concise and readable, reducing the need to write HTML by hand while retaining support for HTML elements and Javadoc tags. This enhancement makes API documentation comments easier to write and read without changing how existing comments are interpreted. Markdown also provides simpler syntax for common elements such as paragraphs, lists, and links, improving maintainability and the developer experience.

### JEP 469: Vector API (Eighth Incubator)

Vector computations consist of a series of operations on vectors. The Vector API expresses these computations so they can be reliably compiled at runtime to optimal vector instructions for supported CPU architectures, outperforming equivalent scalar computations.

The API aims to provide a concise, easy-to-use, platform-independent way to express a wide range of vector computations.

Here is a simple scalar computation over array elements:

```java
void scalarComputation(float[] a, float[] b, float[] c) {
   for (int i = 0; i < a.length; i++) {
        c[i] = (a[i] * a[i] + b[i] * b[i]) * -1.0f;
   }
}
```

Here is the equivalent vector computation using the Vector API:

```java
static final VectorSpecies<Float> SPECIES = FloatVector.SPECIES_PREFERRED;

void vectorComputation(float[] a, float[] b, float[] c) {
    int i = 0;
    int upperBound = SPECIES.loopBound(a.length);
    for (; i < upperBound; i += SPECIES.length()) {
        // FloatVector va, vb, vc;
        var va = FloatVector.fromArray(SPECIES, a, i);
        var vb = FloatVector.fromArray(SPECIES, b, i);
        var vc = va.mul(va)
                   .add(vb.mul(vb))
                   .neg();
        vc.intoArray(c, i);
    }
    for (; i < a.length; i++) {
        c[i] = (a[i] * a[i] + b[i] * b[i]) * -1.0f;
    }
}
```

### JEP 471: Deprecate the Memory-Access Methods in `sun.misc.Unsafe`

JEP 471 deprecated the memory-access methods in `sun.misc.Unsafe`; they are planned for removal in a future release.

Safe and efficient alternatives are available:

- `java.lang.invoke.VarHandle`, introduced in JDK 9 (JEP 193), provides safe and efficient access to heap memory, including object fields, static fields, and array elements.
- `java.lang.foreign.MemorySegment`, introduced in JDK 22 (JEP 454), provides safe and efficient access to off-heap memory and can work with `VarHandle`.

`MemorySegment` is a core type in the Foreign Function & Memory API for safely accessing heap and off-heap memory. `VarHandle` is a separate standard API for accessing fields, array elements, or data through a memory layout. The Foreign Function & Memory API became a permanent feature in JDK 22.

```java
import java.lang.foreign.*;
import java.lang.invoke.VarHandle;

// Manages an off-heap integer array.
class OffHeapIntBuffer {

    // VarHandle for accessing integer elements.
    private static final VarHandle ELEM_VH = ValueLayout.JAVA_INT.arrayElementVarHandle();

    // Memory arena.
    private final Arena arena;

    // Off-heap memory segment.
    private final MemorySegment buffer;

    // Allocates space for the specified number of integers.
    public OffHeapIntBuffer(long size) {
        this.arena  = Arena.ofShared();
        this.buffer = arena.allocate(ValueLayout.JAVA_INT, size);
    }

    // Releases the memory.
    public void deallocate() {
        arena.close();
    }

    // Sets the value at the specified index with volatile semantics.
    public void setVolatile(long index, int value) {
        ELEM_VH.setVolatile(buffer, 0L, index, value);
    }

    // Initializes the specified range to zero.
    public void initialize(long start, long n) {
        buffer.asSlice(ValueLayout.JAVA_INT.byteSize() * start,
                       ValueLayout.JAVA_INT.byteSize() * n)
              .fill((byte) 0);
    }

    // Copies the specified range into a new array.
    public int[] copyToNewArray(long start, int n) {
        return buffer.asSlice(ValueLayout.JAVA_INT.byteSize() * start,
                              ValueLayout.JAVA_INT.byteSize() * n)
                     .toArray(ValueLayout.JAVA_INT);
    }
}
```

### JEP 474: ZGC: Generational Mode by Default

Generational mode becomes the default for the Z Garbage Collector (ZGC). Non-generational mode is deprecated and is planned for removal in a future release, since generational ZGC is a better choice for most workloads.

### JEP 476: Module Import Declarations (Preview)

Module import declarations let Java code import all exported packages from a module without listing each package. This simplifies reuse of modular libraries, especially when using several modules, and makes third-party libraries and core Java classes easier to access.

This feature is especially useful for beginners and prototyping. It avoids requiring developers to modularize their own code, remains compatible with traditional imports, and can make code easier to write and read.

```java
// Import java.base to use types such as List, Map, and Stream without separate imports.
import module java.base;

public class Example {
    public static void main(String[] args) {
        String[] fruits = { "apple", "berry", "citrus" };
        Map<String, String> fruitMap = Stream.of(fruits)
            .collect(Collectors.toMap(
                s -> s.toUpperCase().substring(0, 1),
                Function.identity()));

        System.out.println(fruitMap);
    }
}
```

### JEP 477: Unnamed Classes and Instance Main Methods (Third Preview)

This feature simplifies the `main` method declaration. The traditional form introduces several Java syntax concepts that can make it harder for beginners to get started.

Without this feature, a `main` method looks like this:

```java
public class HelloWorld {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
```

With this feature, it can be written as:

```java
class HelloWorld {
    void main() {
        System.out.println("Hello, World!");
    }
}
```

It can be simplified further by omitting the class name:

```java
void main() {
   System.out.println("Hello, World!");
}
```

### JEP 480: Structured Concurrency (Third Preview)

Structured concurrency was introduced as an incubating API in Java 19. In JDK 23, it is in its third preview. It aims to simplify multithreaded programming, not replace `java.util.concurrent`.

Structured concurrency treats multiple tasks running in different threads as a single unit of work. This simplifies error handling, improves reliability and observability, and preserves the readability and maintainability of single-threaded code.

The core API is [`StructuredTaskScope`](https://openjdk.org/jeps/480). It splits a task into concurrent subtasks that run in their own threads. The subtasks must finish before the parent task continues.

Here is a basic example of `StructuredTaskScope`:

```java
    try (var scope = new StructuredTaskScope<Object>()) {
        // Fork threads to run subtasks.
        Subtask<Integer> subtask1 = scope.fork(task1);
        Subtask<String> subtask2 = scope.fork(task2);
        // Wait for the threads to finish.
        scope.join();
        // Process results or rethrow exceptions.
        ... process results/exceptions ...
    } // close
```

Structured concurrency works well with virtual threads, which are lightweight threads implemented by the JDK. Many virtual threads can share an operating system thread, allowing applications to create large numbers of them.

### JEP 481: Scoped Values (Third Preview)

Scoped values let threads share immutable data, and can be a better fit than thread-local variables, especially when using many virtual threads.

```java
final static ScopedValue<...> V = ScopedValue.newInstance();

// In some method
ScopedValue.where(V, <value>)
           .run(() -> { ... V.get() ... call methods ... });

// In a method called directly or indirectly from the lambda expression
... V.get() ...
```

Scoped values let components in a large program share data safely and efficiently without passing it through method parameters.

### JEP 482: Flexible Constructor Bodies (Second Preview)

This feature was first previewed in JDK 22 as [JEP 447: Statements before `super(...)` (Preview)](https://openjdk.org/jeps/447).

Java requires a `super(...)` or `this(...)` call to be the first statement in a constructor. This prevents a subclass constructor from initializing fields before calling its superclass constructor.

Flexible constructor bodies address this limitation by allowing statements before `super(...)` or `this(...)`. These statements can initialize fields but cannot reference the instance under construction. This helps prevent superclass constructors from calling subclass methods before the subclass fields are initialized.

This feature gives developers more flexibility in organizing constructors. For example, they can validate, prepare, and share data directly in a constructor without relying on helper methods or constructors.

```java
class Person {
    private final String name;
    private int age;

    public Person(String name, int age) {
        if (age < 0) {
            throw new IllegalArgumentException("Age cannot be negative.");
        }
        this.name = name; // Initialize the field before calling the superclass constructor.
        this.age = age;
        // ... other initialization code
    }
}

class Employee extends Person {
    private final int employeeId;

    public Employee(String name, int age, int employeeId) {
        this.employeeId = employeeId; // Initialize the field before calling the superclass constructor.
        super(name, age); // Call the superclass constructor.
        // ... other initialization code
    }
}
```

## JDK 22

### JEP 423: Region Pinning for G1

JEP 423 adds region pinning to the G1 garbage collector to reduce latency caused by Java Native Interface (JNI) critical regions.

Objects in JNI critical regions cannot move during garbage collection. G1 previously handled this by disabling collection, which could block threads and cause high latency. Region pinning lets G1 keep the regions containing those objects in place while collecting other regions, reducing latency and improving throughput and stability when interacting with JNI.

### JEP 454: Foreign Function & Memory API

This API lets Java programs interoperate with code and data outside the Java runtime. It provides efficient calls to foreign functions and safe access to foreign memory, allowing Java programs to use native libraries and data without JNI's risks and fragility.

The Foreign Function & Memory API was incubated in Java 17 through [JEP 412](https://openjdk.java.net/jeps/412), incubated again in Java 18 through [JEP 419](https://openjdk.org/jeps/419), and previewed in Java 19 through [JEP 424](https://openjdk.org/jeps/424), JDK 20 through [JEP 434](https://openjdk.org/jeps/434), and JDK 21 through [JEP 442](https://openjdk.org/jeps/442).

The API became a permanent feature in JDK 22.

For more details, see [New Features in Java 19](./java19.md).

### JEP 456: Unnamed Variables and Patterns

Unnamed variables and patterns were previewed in JDK 21 through [JEP 443](https://openjdk.org/jeps/443) and became permanent in JDK 22.

For details, see [New Features in Java 21](./java21.md).

### JEP 458: Launch Multi-File Source-Code Programs

Java 11 introduced [JEP 330: Launch Single-File Source-Code Programs](https://openjdk.org/jeps/330), which lets the `java` launcher run a single Java source file directly. With `java HelloWorld.java`, Java compiles the source in memory and runs it without writing `.class` files to disk. This makes it easier to write small utilities and try out Java without a separate compilation step.

Suppose `Prog.java` declares two classes:

```java
class Prog {
    public static void main(String[] args) { Helper.run(); }
}

class Helper {
    static void run() { System.out.println("Hello!"); }
}
```

The `java Prog.java` command compiles both classes in memory and runs the `main` method of the first class declared in the file.

One limitation is that all source code must be in a single `.java` file.

[JEP 458: Launch Multi-File Source-Code Programs](https://openjdk.org/jeps/458) extends JEP 330 to let you run programs made up of multiple Java source files without an explicit compilation step.

Suppose a directory contains two Java source files, `Prog.java` and `Helper.java`, each declaring a class:

```java
// Prog.java
class Prog {
    public static void main(String[] args) { Helper.run(); }
}

// Helper.java
class Helper {
    static void run() { System.out.println("Hello!"); }
}
```

When you run `java Prog.java`, the Java launcher compiles the source in memory and runs `Prog.main`. Since `Prog` references `Helper`, the launcher finds `Helper.java` in the file system, compiles it, and loads the class automatically. You do not need to call `javac` on each source file.

This feature makes it easier to grow from a small program to a larger one. Developers can choose when to add a build tool, without setting up a complex project structure during rapid iteration. It is useful for prototypes, experiments, and early-stage projects.
